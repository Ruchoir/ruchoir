# AGENTS.md

Guidance for AI coding agents and human contributors working in this repository.
This is the single source of operational context for the project. Read it fully before
making changes. The nearest `AGENTS.md` to the file you are editing takes precedence.

## Project overview

Ruchoir (working codename - final name TBD) is a French, sovereign, open-core alternative
to Slack, Mattermost and Nextcloud: a single professional workspace combining real-time team
messaging and file sharing. Its signature feature is a zero-loss import tool that migrates an
existing Nextcloud or Mattermost instance into Ruchoir in under two minutes.

Web interface only for now. The core is open source under **AGPLv3**.

## Golden rules (read first)

1. **No AI references anywhere in this repository - ever.** Not in code, comments, commit
   messages, branch names, PRs, docs, or metadata. No `Co-Authored-By` trailers naming an AI,
   no "generated by" notes, no agent signatures. **This file (`AGENTS.md`) is the only
   AI-facing file allowed in the repo.** Write and commit exactly as a human contributor would.
2. **No US or non-European dependencies - non-negotiable.** No US/non-EU hosted services at
   runtime (no AWS/GCP/Azure, no Google Fonts, no US CDN, no outbound telemetry). For libraries,
   prefer a European or neutral community alternative over any package governed by a US/non-EU
   entity when functionally equivalent (e.g. use the community `rust-s3`, not `aws-sdk-s3`).
   Before adding any new dependency, check and document its origin/governance; when in doubt, ask.
3. **English only** for everything in the repo: code, identifiers, comments, docs, commits,
   branches, issues, PRs.
4. **Document thoroughly**, following current industry best practices (module docs, docstrings,
   ADRs for structural decisions).
5. **Keep docs current, unprompted.** When a change alters a decision, the stack, scope, or a
   convention, update `README.md`, this file and the nearest `AGENTS.md` in the same change so
   they never drift. Record non-obvious gotchas here so they are not hit twice.
6. **No em dashes (the U+2014 character) anywhere** in code, comments, docs, or commits. Use a
   colon, comma, parentheses, or a plain hyphen instead.

## Tech stack

> Pin and keep exact versions here as soon as they are chosen. Do not change them without an
> explicit decision.

- **Backend / API:** Rust (edition 2021+), async `tokio`, web framework `axum`.
- **Real-time:** native WebSocket (axum/tokio) with **SSE fallback** for constrained networks.
- **Frontend:** Next.js + React + TypeScript + Tailwind CSS, built as a **static export** (no SSR,
  no Server Actions, no Next API routes). **No Node in production:** the static bundle is served by
  the Rust API. Next.js is a build tool only.
- **Database:** PostgreSQL (source of truth) + Valkey (presence, real-time pub/sub, cache, sessions).
  Valkey (Linux Foundation, BSD-3) is the key-value store; it speaks the Redis protocol (RESP), so
  the usual Rust clients work unchanged. Chosen over Redis for neutral governance (2026-08-29).
- **Object storage:** Garage (S3-compatible, Rust, AGPLv3) via an S3 abstraction. Client: `rust-s3`.
- **Auth:** native in the Rust API (argon2id password hashing, opaque server sessions in Valkey,
  TOTP + WebAuthn/passkeys, encrypted recovery keys). `webauthn-rs` pulls OpenSSL to validate
  attestation certificates, so the API image installs `libssl-dev` to build and `libssl3` to run.
  That is a crypto library inside a dependency, not a TLS backend: transport TLS stays rustls with
  the `ring` provider. A development machine usually has both already, which is why this only
  surfaced when the image was first built on a clean host. Optional OIDC connectors for Google and
  Microsoft, disabled by default (opt-in, see Golden rule #2). No Node-side auth.
- **Containerization:** Docker + `docker compose` (all-in-one deployment).

## Languages

The interface speaks French, English, Spanish, German, Italian and Polish. **French is the source
language**: it is what the product is written in, what a missing key falls back to, and what the
other five translate. Its dictionary is the contract, so a key added to `fr.json` fails the build of
the other five until they carry it.

- Dictionaries: `apps/web/lib/i18n/dictionaries/<locale>.json`, bundled rather than fetched (a
  self-hosted instance must not download its own interface twice).
- Runtime: i18next + react-i18next. Chosen over FormatJS/react-intl partly for governance: i18next is
  developed in Europe, react-intl is US-governed, and between two MIT libraries that both run
  locally, the sovereign one costs nothing.
- Choosing a language: the person's preference, then the browser, then French. A chosen language is
  also sent to the account (`users.locale`), because the server writes too, and an address
  confirmation must not arrive in a language its reader did not ask for.
- Server-side text (three emails) lives in `apps/api/src/auth/mail_text.rs`, in the same six
  languages, with no translation crate: three messages do not justify a dependency and a loader.

**`pnpm --filter @ruchoir/web i18n:check` (CI runs it) fails on any user-visible string typed into a
component, and on any disagreement between the six dictionaries.** A string that is not prose goes in
that script's `ALLOWED` list, with the reason. Files still written in French are listed in
`apps/web/tools/i18n-audit/untranslated.json`: **that list only ever shrinks**, nothing may be added
to it, and a new screen is written translated from the start.

## Setup commands

See `docs/development.md` for the full workflow, and `docs/deployment.md` for putting an
instance in front of real people. Quick reference:

- Configure env: `cp .env.example .env` (never commit `.env`).
- Build the web export: `pnpm install && pnpm --filter @ruchoir/web build`.
- Run the API (serves the export at http://localhost:8080): `cargo run -p ruchoir-api`.
- Full stack: `docker compose up --build`.
- Optional dev TLS: `scripts/dev-tls.sh`, then `cargo run -p ruchoir-api --features tls`.

## Architecture notes

- The Rust API is stateless (shared state in Postgres/Valkey) so it can run behind a load balancer.
  It also serves the frontend's static bundle; there is a single production service.
- The Rust API never trusts the client: every request is authenticated and authorized server-side.
- **Auth:** fully owned by the Rust API. Passwords are argon2id; sessions are opaque server-side
  records in Valkey delivered as `httpOnly`+`Secure`+`SameSite` cookies. The frontend holds no auth
  secret. Define argon2id params, session lifetime and the WebAuthn flow before broad work.
- **Storage:** all file operations go through the S3 abstraction; the backend (Garage by default)
  is interchangeable and never hard-coded.
- **Fonts:** self-host IBM Plex Sans/Mono (OFL) via local `@font-face`. Never depend on Google Fonts.

## Security & compliance ("everything encrypted, nothing in clear")

Encryption model: strong encryption **at rest and in transit** (not end-to-end at the MVP; the
server can read content to power search, previews and import). No sensitive data in clear anywhere,
including logs.

- **In transit:** TLS everywhere (reject plaintext HTTP), `wss://` only, HSTS; aim for TLS/mTLS
  between internal services.
- **At rest:** encrypt the database, object storage and backups; buckets private, short-lived
  signed URLs.
- **Auth/sessions:** argon2id passwords, opaque server sessions, MFA, rate limiting, server-side
  authorization on every request.
- **Secrets:** never in the repo (`.env` gitignored, provide `.env.example`); prefer a European or
  neutral secret store (e.g. OpenBao) over US-governed ones.
- **Hardening:** strict CSP and security headers, parameterized SQL, input validation, Markdown
  sanitization, safe uploads, `cargo audit` / npm audit.
- **Logs:** never log passwords, tokens, secrets, or private message content.
- **GDPR:** data minimization, per-user data export and deletion.
- **Import archives** are encrypted, may contain secrets: never log in clear, purge after use.
